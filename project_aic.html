Multimodal Video Retrieval System

A multimodal search engine for retrieving relevant frames from large-scale news and event footage using visual, textual, and spoken content.

Python PyTorch CLIP PaddleOCR FAISS Gradio

A search engine over a 300GB corpus of news and event footage that allows users to find relevant frames by describing what is visually happening, what is written on screen, or what was said.

300GB video corpus
175K+ indexed keyframes
<1s query latency
4 vision encoders
Problem

Large video collections contain information across several different modalities. A relevant moment may be recognizable from the visual scene itself, from text displayed on screen, or from something spoken in the video.

A retrieval system based on only one of these signals can therefore miss relevant content. The goal of this project was to build a retrieval pipeline capable of searching across these different information sources within a large frame corpus.

Approach

I designed a multimodal retrieval pipeline that separates visual, textual, and audio information into dedicated processing stages, then exposes the resulting search capabilities through a unified interface.

System Architecture
  • Video → Keyframes: extracted representative frames from the source videos to create the searchable image corpus.
  • Visual retrieval: generated image embeddings with SigLIP2, CLIP, FG-CLIP, and LAION-CLIP.
  • OCR retrieval: extracted on-screen text from frames using PaddleOCR.
  • Audio retrieval: indexed spoken content through YouTube subtitle extraction and Whisper.
  • Vector search: used FAISS for approximate nearest-neighbor retrieval over image embeddings.
  • Visualization and interface: used FiftyOne for dataset inspection and Gradio for interactive retrieval.
Technical Challenges
  • Large-scale indexing: processing a 300GB corpus required separating extraction, embedding, OCR, and indexing into independent stages.
  • Limited compute resources: expensive embedding extraction had to be distributed across remote GPU resources and interruptible Kaggle GPU sessions.
  • Multimodal relevance: visual similarity, OCR matching, and spoken content capture different types of relevance and therefore require different retrieval paths.
  • Device limitation: Our laptops lacked the compute resources required for local inference, so we offloaded the workload to a rented GPU server, accessed it via SSH, and deployed the application through Cloudflare to enable lightweight client-side usage.
Engineering Decisions

Why multiple vision encoders?

As part of the competition, our team explored multiple vision-language models in parallel. Each team member worked with a different model, allowing us to compare their retrieval performance and characteristics across the same dataset: SigLIP2, CLIP, FG-CLIP, and LAION-CLIP.

Why FAISS?

The indexed embeddings required efficient nearest-neighbor search over a large collection of vectors. FAISS provided approximate vector retrieval without requiring a separate distributed vector database, keeping the deployment relatively lightweight.

The current system supports multimodal retrieval across visual content, on-screen text, and spoken content.

What I Built
  • End-to-end keyframe extraction and indexing pipeline.
  • Multi-model visual embedding pipeline for comparative retrieval experiments.
  • GPU-based OCR processing pipeline with PaddleOCR.
  • FAISS-based approximate nearest-neighbor retrieval system.
  • Audio transcription and spoken-content indexing pipeline.
  • Interactive retrieval interface using Gradio.
  • Dataset inspection and retrieval-result analysis using FiftyOne.
  • Checkpointing and resumable processing for interruptible GPU environments.
Constraints

The system was developed without dedicated compute infrastructure. Expensive embedding extraction and preprocessing tasks were distributed across remote GPU servers accessed through SSH and Kaggle GPU sessions.

Constraint-driven engineering: remote sessions could be interrupted or reclaimed, so the processing pipeline had to checkpoint intermediate outputs and resume from completed stages rather than starting the entire computation again.
